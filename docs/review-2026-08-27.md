## Confirmed findings

### 1. [P2] Resolve font-relative lengths before geometry arithmetic

Location: [src/node.typ:982](../src/node.typ#L982), with analogous edge-bound
handling in [src/diagram.typ:90](../src/diagram.typ#L90). Numeric conversion
eventually fails in [src/geometry.typ:134](../src/geometry.typ#L134) or
[src/shape.typ:83](../src/shape.typ#L83).

`min-size: 1em` passes validation, but node preparation scales it without
resolving its font-relative component. A clipped circle then fails with
`cannot divide these two lengths`; a polygon fails during outline
validation. Gate `size: 1em` and edge `stroke: 0.1em + black` also fail in
mixed-length comparisons. This breaks otherwise-valid font-responsive
themes. `diagram(scale: 2em)` already resolves its scale correctly.

Suggested change: normalize core geometric lengths at the contextual layout
boundary before fit, comparison, and numeric conversion. Cover node minima,
insets, radii, gate sizes/spacing, part transforms, marks, and edge stroke/
highlight lengths; preserve ratios and resolve only the length component of
relative values. Keep pure helpers usable with already-absolute lengths.

Evidence (now passing): `tests/regressions/font-relative-{node,polygon,gate,stroke}.typ`.
`tests/documentation-contract.typ` now exercises direct `em` inputs without
the original `.to-absolute()` workaround.

### 2. [P2] Include displaced highlight joins in diagram bounds

Location: [src/diagram.typ:101](../src/diagram.typ#L101).

`edge-visual-radius` budgets `abs(offset) + width/4`, while
`offset-polyline` can displace a miter joint by up to four times the offset.
For `(0,0) -> (10,0) -> (0,2)` in points, a 4pt highlight with no central
stroke extends its centerline about 3.98pt beyond the rightmost waypoint,
but receives only 2pt of bound expansion, even before the band's own stroke.
Tight exports or neighboring content can therefore crop/overlap the band.

Suggested change: derive highlight bounds from the same displaced paths used
for painting and include their actual stroke/cap/join outsets, or use a
proven conservative bound incorporating both miter stages. Avoid a fix that
only works when the central wire's thickness happens to hide the problem.

Evidence (now passing): `tests/regressions/highlight-bounds.typ` asserts that
the painted bands fit, including acute turns, zoom, and curved paths.

### 3. [P2] Account for square-cap projection on diagonal wires

Location: [src/diagram.typ:91](../src/diagram.typ#L91).

Single-segment edges request a non-miter outset and receive exactly half the
stroke thickness on each axis. A square cap on a 45-degree line contributes
both tangent and normal projections. With a 10pt stroke, the diagram needs
approximately 14.142pt of total horizontal expansion, but reports 10pt.
This affects explicit square caps; the default butt cap is unaffected.

Suggested change: include cap type and endpoint direction when bounding
open paths, or use the conservative square-cap axis bound. Keep closed-node
outsets separate so fixing open paths does not unnecessarily enlarge nodes.

Evidence (now passing): `tests/regressions/square-cap-bounds.typ`, using an actual measured
public `diagram()` with `baseline: 0pt`.

### 4. [P2] Do not expose unresolved config `auto` as a concrete setting

Location: [src/diagram.typ:925](../src/diagram.typ#L925).

`pick` substitutes a configured value without checking whether that value
is itself `auto`. `typ.config(scale: auto)[#typ.diagram(...)]` therefore
fails the scale assertion, although `diagram(scale: auto, ...)` is valid
and config advertises the corresponding non-theme options. Settings such
as `grid` have the same problem. This makes forwarding optional settings
through a reusable config wrapper unsafe.

Suggested change: explicitly define config's automatic-value semantics—skip
inheritance/no-op versus reset-to-package-default—and implement that policy
at stack insertion or fallback resolution. Preserve the intentionally valid
resolved `auto` values for `font-size` and `baseline`.

Evidence (now passing): `tests/regressions/config-auto.typ`. Additional passing config
tests cover nested restoration and concrete renderer overrides.

### 5. [P2] Handle zero-size built-in polygon nodes consistently

Location: [src/shape.typ:427](../src/shape.typ#L427); the same pattern occurs
in other polygon-based built-ins.

An unlabeled node with only `shape: typ.shapes.diamond` gets zero width and
height from neutral defaults, then passes coincident vertices into polygon
validation and fails compilation. The public arbitrary-polygon factory
already avoids this with a nonzero fallback. A basic shape selection should
not unexpectedly turn an otherwise-valid neutral node into an invalid
outline.

Suggested change: choose and document a consistent policy for zero-requested
polygon geometry (a normalized fallback, or an empty outline), applying it
across built-ins. Do not weaken validation of genuinely malformed custom
polygons.

Evidence (now passing): `tests/regressions/zero-size-polygon.typ`. Positive-size shapes
remain covered by the existing and new geometry suites.

### 6. [P2] Fit a circle to the complete label rectangle

Location: [src/shape.typ:147](../src/shape.typ#L147).

Multiplying the larger label dimension by 1.2 does not contain the corners
of square-like content. A 20pt square produces a 12pt circle radius, but its
corners require approximately 14.142pt. The label is included in diagram
bounds, yet visibly protrudes outside the claimed fitted silhouette.

Suggested change: derive the needed radius from the farthest label-box
corner, including any inset-induced displacement, while honoring explicit
minima. Retain tests for thin labels and asymmetric padding to avoid
excessive enlargement or off-center clipping.

Evidence (now passing): `tests/regressions/circle-label-fit.typ` measures a real rectangular
label rather than assuming a particular font's glyph dimensions.

## Maintainability and security observations

- [src/node.typ:743](../src/node.typ#L743) duplicates the simple bounds logic
  in `_outline-size-simple` at line 369. Delegate the non-composite branch
  to the shared helper in a future refactor; the new bounds tests provide
  a guard against divergence. This was not changed during the review.
- [src/style.typ:114](../src/style.typ#L114) declares `allow-auto` but never
  reads it. Remove it or implement the advertised restriction before
  callers rely on passing `false`.
- The renderer contains no authentication, SQL, shell execution, or
  application-network boundary to audit. Its extensibility boundary is
  caller-provided Typst builder code and open node-style dictionaries.
  No concrete exploitable security issue was identified; this is not a
  security certification.
- Validation remains intentionally incomplete for polygon simplicity and
  custom extension fields. Large or adversarial documents can still be
  expensive; a host compiling untrusted Typst should enforce its own
  resource limits. No production validation was relaxed.

## Performance and verification

The core already caches visual preparation, uses small lookup buckets, and
precomputes factory geometry. No runtime optimization was attempted. A
single local warm run with Typst 0.15.1 took 0.31s for `stress.typ` (400
nodes / 760 edges), 0.28s for `shape-stress.typ`, and 0.24s for
`curve-stress.typ`. These are observational timings, not portable thresholds
or a before/after speedup claim. Identity buckets with many unequal nodes
sharing the same cheap key remain a potential worst-case quadratic path.

Initial review coverage: four positive Typst suites, expanded config contracts, 38
negative fixtures, nine Python SVG-helper tests, and nine known-issue
reproductions. At that stage, the test runner reported `XFAIL` distinctly
and rejected unexpected successes. The implementation follow-up promoted
these files and removed the expected-failure registry.

Verified at the end of the initial review (superseded by final results above):

- `bash tests/run.sh`: 16 positive Typst fixtures, 113 negative fixtures,
  nine Python tests, one outline snapshot, and six generated documentation
  SVGs pass; nine known-issue reproductions still fail as expected.
- `bash -n tests/run.sh` and `git diff --check`: pass.
- `quarto render docs/quarto` with Quarto 1.10.18: all 19 pages build.
- Generated HTML check: 1,706 local file/anchor references, no broken targets.

Residual limits: no cross-platform run, full fuzzing, or blanket execution
of every prose code listing; companion-package implementations were outside
this review. Existing curve-sampling detection limits and SVG text-based
quantization are documented, not claimed to be eliminated.
